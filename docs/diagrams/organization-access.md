# Кабинет организации: выдача доступа, команда и пароль

Кабинет принадлежит организации, а не отдельному сотруднику. Публичной регистрации нет: будущий клиент сначала оставляет заявку на демо, администратор Smailee проводит демо и создаёт организацию с владельцем. При штатном создании постоянный пароль генерируется сервером и отправляется только клиенту; администратору он не показывается. Временный пароль — отдельный аварийный сценарий: его вручную задаёт администратор, после чего клиент обязан заменить его. Все пароли хранятся только в виде bcrypt-хеша, а ссылки приглашения и восстановления — только как SHA-256-хеш одноразового токена.

```mermaid
flowchart TD
  Visitor([Посетитель лендинга]) --> Demo[Оставляет заявку на демо<br/>имя, компания, контакт и источник CTA]
  Demo --> SavedLead[Заявка всегда сохраняется в БД и админке<br/>копия best-effort уходит в общий Битрикс24]
  SavedLead --> DemoCall[Команда Smailee проводит демо]
  DemoCall --> ServiceAdmin[Администратор Smailee создаёт кабинет по email]
  ServiceAdmin --> GeneratedAccess[Генерируется криптографический<br/>первоначальный пароль]
  GeneratedAccess --> Account[Одной транзакцией создаются владелец,<br/>организация и демо «Стандартного» на 14 дней]
  Account --> AccessMail{Системное письмо отправлено?}
  AccessMail -->|да| Credentials[Клиент получает логин, пароль<br/>и ссылку «Войти»]
  Credentials --> RegularLogin[Вход без обязательной смены пароля]
  RegularLogin --> Terms
  AccessMail -->|нет| Repair[Админ вручную задаёт<br/>временный пароль]
  ServiceAdmin --> Repair
  Repair --> OneTime[Временный пароль показывается админу<br/>для ручной передачи клиенту]
  OneTime --> FirstLogin[Вход с временным паролем]
  FirstLogin --> Forced[Обязательная смена:<br/>новый пароль + подтверждение]
  Forced --> Terms{Соглашение уже принято?}
  Terms -->|нет| Accept[Принять пользовательское соглашение]
  Terms -->|да| Login
  Accept --> Login[Кабинет организации]
  Login --> Owner{Это владелец и первичная<br/>настройка не завершена?}
  Owner -->|да| Onboarding[Онбординг из 6 шагов<br/>см. «Подготовка»]
  Owner -->|нет| Check
  Onboarding --> Check

  OrgAdmin([Администратор организации]) --> Team[Настройки → Команда]
  Team --> Email[Указывает email сотрудника]
  Email --> Rights[Выбирает шаблон или отдельные доступы]
  Rights --> Invite[Создаётся сотрудник и одноразовая ссылка]
  Invite --> InviteMail{Системный SMTP настроен?}
  InviteMail -->|да| Received[Сотрудник получает письмо]
  InviteMail -->|нет| Saved[Сотрудник добавлен,<br/>ссылку можно отправить повторно]
  Saved --> Invite
  Received --> SetPassword[Сотрудник вводит пароль и подтверждение<br/>может показать пароль]
  SetPassword --> Token{Ссылка валидна<br/>и не использована?}
  Token -->|нет| NewLink[Запросить новую ссылку]
  NewLink --> Invite
  Token -->|да| Login

  Check{Какие доступы включены?}
  Check --> Default[Сразу открывается первый доступный раздел<br/>или экран «Нет назначенных доступов»]
  Check --> Contacts[База контактов: просмотр / управление]
  Check --> Campaigns[Кампании: свои или все;<br/>контакты получателей — отдельный доступ]
  Check --> Stats[Аналитика коммуникаций<br/>по праву просмотра статистики]
  Check --> Leads[Inbox: диалоги своих кампаний или все]
  Check --> Infra[Инфраструктура<br/>по отдельному праву]
  Check --> Billing[Тариф и оплата<br/>по отдельному праву]
  Check --> Settings[Настройки организации и команда]
  Settings --> BusinessProfile[Профиль организации:<br/>сайт по умолчанию, ручной ввод без сайта,<br/>проверка и публикация]
  BusinessProfile --> ProfileFlow[Отдельный путь<br/>см. business-profile.md]
  Check --> Integrations[Интеграции: Битрикс24 и Telegram]
  Settings --> AdminOnly{Администратор организации?}
  Integrations --> AdminOnly
  AdminOnly -->|да| Manage[Управляет настройками и командой]
  AdminOnly -->|нет| Denied([Раздел недоступен])

  Visitor --> SignIn[На лендинге доступен только вход<br/>без публичной регистрации]
  SignIn --> Login
  SignIn --> Forgot[«Забыли пароль»]
  Login --> Forgot
  Forgot --> ResetEmail[Ссылка восстановления на email]
  ResetEmail --> ResetToken{Ссылка валидна<br/>и не использована?}
  ResetToken -->|нет| Forgot
  ResetToken -->|да| ResetPassword[Новый пароль + подтверждение]
  ResetPassword --> Login

  Check --> AI[Генерация/автоответ ИИ]
  AI --> API{Общий AI API доступен?}
  API -->|да| AIGenerated[Генерация или черновик ответа]
  API -->|нет| AIError[Показать «ИИ сейчас недоступен»<br/>ничего не подставлять и не отправлять]
  AIError --> Incident[Баннер администраторам организации<br/>+ глобальное письмо с no-reply на ADMIN_EMAIL<br/>после 3 ошибок, не чаще раза в сутки]
```

Доступы проверяются на сервере для каждого действия, а не только скрывают кнопки. Если для страницы доступна лишь часть действий, недоступные элементы остаются серыми и объясняют причину при нажатии. Право «Контакты получателей кампании» дополнительно защищает имя, компанию, email и персональный предпросмотр письма. Сотрудник работает с общими данными организации; автор кампании фиксируется отдельно, чтобы ограничение «только свои кампании/лиды» было проверяемым. «Инфраструктура» и «Тариф и оплата» могут быть выданы сотруднику отдельными правами; «Настройки» и «Интеграции» доступны только администратору организации.

Недоступность общего API фиксируется как инцидент: баннер видит только администратор организации. Уведомление отправляется системной почтой с `SYSTEM_MAIL_FROM` на `ADMIN_EMAIL` после трёх последовательных ошибок и не чаще одного раза в сутки; несколько событий объединяются в дайджест. При следующем успешном запросе инцидент закрывается автоматически.
