# Диаграммы процессов

Пользовательские пути продукта. Источник правды по тому, **что и в каком
порядке происходит с точки зрения пользователя** — в отличие от
`docs/tz/cold-outreach-mailbox-model.md`, который отвечает на вопрос «почему
архитектура устроена так».

## Принцип разбиения

Каждая диаграмма — процесс с **началом, всеми развилками и концом**. Не
отдельная функция и не экран, а путь целиком: если у чего-то нет
самостоятельного конца, оно не отдельный процесс, а часть другого.

Отсюда, например, следует, что создание кампании, отправка, ИИ-диалог и
передача лида — **один** процесс, а не четыре: кампания не завершена, пока по
каждому контакту не наступил финал.

| Процесс | Начало | Конец |
|---|---|---|
| [Подготовка](infrastructure.md) | Регистрация | Прогретый рабочий ящик |
| [База контактов](contacts.md) | Файл с базой | Контакты готовы к кампании |
| [Рассылка](campaign.md) | Решение создать кампанию | Линия закрыта по каждому контакту |
| [Тариф](billing.md) | Упёрлись в лимит | Лимиты подняты |
| [Кабинет организации](organization-access.md) | Приглашение сотрудника | Доступ в общий кабинет с назначенными правами |

## Как править

**Через GitHub** — открыть файл, карандаш, править код диаграммы, вкладка
Preview показывает результат, коммит уходит в репозиторий.

**Через живой редактор** — если удобнее видеть картинку на каждый символ:

```bash
npm run diagram:link docs/diagrams/campaign.md
```

Открыть ссылку, поправить, скопировать адрес из адресной строки и вернуть:

```bash
npm run diagram:pull docs/diagrams/campaign.md "<ссылка>"
```

Обратный путь трогает только код внутри mermaid-блока — пояснительный текст
вокруг диаграммы остаётся на месте.

## Чего здесь нет

Внутренней механики: как устроен захват партии писем, как классифицируются
ошибки почтового сервера, как работает ротация ящиков. Это уровень ниже —
он живёт в комментариях кода и в ТЗ. Диаграммы меняются, когда меняется
путь пользователя, и молчат на внутренних правках.

## Правило

**Любая фича или правка кода, меняющая путь пользователя, отражается на
диаграмме — в том же коммите.** Не отдельной задачей «потом обновим».

Если непонятно, на какую из четырёх диаграмм ложится изменение — это не
повод пропустить. Это сигнал, что процесс упущен и нужна пятая (или шестая)
диаграмма, а не что диаграммы можно оставить как есть.

Перед коммитом — проверить синтаксис рендером (`npm run diagram:link` и
посмотреть в mermaid.live, либо вкладка Preview на GitHub). Битый mermaid
GitHub тихо показывает как обычный текст, без ошибки — есть шанс не
заметить.
