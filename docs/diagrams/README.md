# Диаграммы процессов

Пользовательские пути продукта. Источник правды по тому, **что и в каком
порядке происходит с точки зрения пользователя** — в отличие от
`docs/tz/cold-outreach-mailbox-model.md`, который отвечает на вопрос «почему
архитектура устроена так».

Последняя полная сверка с `main`: **17 августа 2026 года**. В неё входят
организации и права сотрудников, закрытая регистрация, 14-дневное демо
«Стандартного», заморозка без оплаты, причины статуса «В очереди»,
автопереподключение ящиков, Битрикс24, персональные Telegram-уведомления и
настраиваемые email-дайджесты.
Также отражён единый профиль организации: автоматическое заполнение по сайту, ручной путь без сайта, вопросы ИИ и публикация версии.

## Принцип разбиения

Каждая диаграмма — процесс с **началом, всеми развилками и концом**. Не
отдельная функция и не экран, а путь целиком: если у чего-то нет
самостоятельного конца, оно не отдельный процесс, а часть другого.

Отсюда, например, следует, что создание кампании, отправка, ИИ-диалог и
передача лида — **один** процесс, а не четыре: кампания не завершена, пока по
каждому контакту не наступил финал.

| Процесс | Начало | Конец |

| [База контактов](contacts.md) | Файл с базой | Контакты готовы к кампании |
| [Рассылка](campaign.md) | Решение создать кампанию | Линия закрыта по каждому контакту |
| [Inbox](inbox.md) | В кампанию приходит ответ | Диалог отвечен, обработан или передан дальше |
| [Тариф](billing.md) | Кабинет создан с демо «Стандартного» | Оплаченный доступ или замороженный кабинет |
| [Кабинет организации](organization-access.md) | Заявка на демо или приглашение сотрудника | Доступ в общий кабинет с назначенными правами |
| [Интеграции](integrations.md) | Администратор настраивает CRM или сотрудник подключает личный Telegram | CRM и/или личный Telegram подключены либо явно отключены |

## Как проходить вручную

Сплошная стрелка — действие или автоматический переход, который должен быть
виден в текущем пользовательском пути. Пунктирная — ожидание внешнего события
или возврат к процессу позже. Для полной приёмки нужно пройти каждую развилку,
а не только самый короткий успешный маршрут.

Ограничения, которые сейчас являются частью продукта, а не ошибкой теста:

- публичной регистрации нет — кабинет создаёт администратор Smailee;
- платёжный шлюз пока не подключён: кнопка оплаты создаёт платёж `PENDING`,
  после чего его подтверждает администратор или совместимый вебхук;
- HTML-шаблоны, картинки и визуальный редактор писем архивированы; в продукте
  остаются текстовые письма и минимальный HTML только для Open Rate;
- основной ИИ-провайдер — DeepSeek; при его сбое фиктивный текст не подставляется.

## Известные расхождения реализации

Во время сверки 13 августа 2026 года найдены сценарии, где интерфейс и
серверные права пока расходятся. Они не считаются нормальным поведением;
если расхождение затрагивает сам путь, оно прямо помечено на диаграмме как
дефект. При ручной приёмке нужно фиксировать следующее:

1. Кнопка «Передать в CRM вручную» показывается любому сотруднику, который
   видит лид и подключённый Битрикс24, но серверное действие сейчас разрешено
   только администратору организации.
2. Право `CAMPAIGNS_CREATE` можно выдать без `CAMPAIGNS_MANAGE_OWN`: сотрудник
   создаст кампанию, но не сможет запустить созданную собой кампанию.
3. При автоматическом срабатывании сигнала передачи движок сначала создаёт
   ответ ИИ (а без модерации может успеть отправить его) и только затем
   обращается в CRM. При успешной передаче уже созданный черновик также не
   отзывается автоматически.
4. Заявка с лендинга передаётся в общий Битрикс24 с `SOURCE_ID=WEB`; требуемое
   ранее значение источника `form` сейчас не реализовано.
5. Метрика «Доставлено» на странице аналитики не является подтверждением доставки:
   после принятия письма SMTP-сервером выставляется только статус `SENT`, а
   перехода в `DELIVERED` в текущем движке нет. Поэтому значение обычно
   увеличивается лишь после открытия, клика или ответа.
6. Визард считает шаг «Прогрев» завершённым только после запуска прогрева, но
   `/app` и баннер незавершённой настройки этот шаг не проверяют. Если остальные
   данные уже созданы, администратор может выйти из обязательного онбординга с
   выключенным прогревом.

## Как править

**Через GitHub** — открыть файл, карандаш, править код диаграммы, вкладка
Preview показывает результат, коммит уходит в репозиторий.

**Через живой редактор** — если удобнее видеть картинку на каждый символ:

```bash
npm run diagram:link docs/diagrams/campaign.md
```

Открыть ссылку, поправить, скопировать адрес из адресной строки и вернуть:

```bash
npm run diagram:pull docs/diagrams/campaign.md "<ссылка>"
```

Обратный путь трогает только код внутри mermaid-блока — пояснительный текст
вокруг диаграммы остаётся на месте.

## Чего здесь нет

Внутренней механики: как устроен захват партии писем, как классифицируются
ошибки почтового сервера, как работает ротация ящиков. Это уровень ниже —
он живёт в комментариях кода и в ТЗ. Диаграммы меняются, когда меняется
путь пользователя, и молчат на внутренних правках.

## Правило

**Любая фича или правка кода, меняющая путь пользователя, отражается на
диаграмме — в том же коммите.** Не отдельной задачей «потом обновим».

Если непонятно, на какую из существующих диаграмм ложится изменение — это не
повод пропустить. Это сигнал, что процесс упущен и нужна пятая (или шестая)
диаграмма, а не что диаграммы можно оставить как есть.

Перед коммитом — проверить синтаксис рендером (`npm run diagram:link` и
посмотреть в mermaid.live, либо вкладка Preview на GitHub). Битый mermaid
GitHub тихо показывает как обычный текст, без ошибки — есть шанс не
заметить.
